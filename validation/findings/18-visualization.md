# Finding 18 — Visualization (Phase 11)

Status: **5 of the plan's 7 planned figures built; 2 explicitly skipped,
for real reasons tied to earlier findings, not omitted silently.**
Vector PDFs under `validation/figures/`, generated by
`validation/analysis/generate_figures.py` from three CSVs, each itself
produced by a small script that decodes the actual campaign capture
files directly rather than transcribing numbers out of a markdown table
(`compute_density_summary.py`, `etm_overhead_summary.py`, and the
already-existing `aggregate_pipeline_metrics.py` from Finding 13).
All three CSVs, and every figure below, were regenerated a second time
after Finding 11's not-taken-branch fix changed `instructionsReconstructed`
campaign-wide — the numbers here match Findings 06/10/13/14's own
post-fix numbers exactly, since they come from the identical scripts.

Style, per explicit direction this session: black/white/grey only, no
categorical color palette; a restrained blue/red pair reserved
exclusively for the one chart with a real two-series comparison
(pipeline decode vs. transform timing), never used for bars or the
schematic diagram.

## Figures built

1. **`fig01_density_by_workload.pdf`** — instructions/byte by workload,
   mean ± stdev bars, ordered by Finding 10's own density ranking.
2. **`fig02_branch_density_vs_density.pdf`** — branch density vs.
   instruction density scatter, direct-labeled (no legend needed for a
   single series), Pearson r annotated with an explicit "not an
   inferential regression" caveat inline, matching Finding 10's own
   framing rather than letting the number stand unqualified.
3. **`fig03_etm_overhead.pdf`** — two panels rather than one grouped bar,
   because the four ETM configurations split into two wildly different
   magnitudes (0% vs. ~99% change) that would make a single linear
   y-axis unreadable: panel (a) retstack/branch-broadcast at a zoomed
   scale (so W4's real but small -3.1% retstack effect is visible),
   panel (b) timestamp+cyclecount's collapse. Uses the corrected
   numbers from Finding 14, not Finding 06's retracted ones — freshly
   re-decoded from `etm_sweep_cti/*/capture.bin` directly, confirming
   the corrected magnitude (-98.4% to -100.0%) rather than trusting
   either finding's transcribed table.
4. **`fig04_pipeline_scaling.pdf`** — two panels, decode time and
   transform time vs. instruction count, from Finding 13's own
   `pipeline_metrics.csv` (n=36). Axis labeled "instructions
   reconstructed," not "size," matching Finding 13's own honest
   correction that byte count is constant across every capture in this
   campaign.
5. **`fig05_fault_case_study.pdf`** — a schematic, not a statistical
   chart: two bordered panels, state-at-halt register values on the
   left, the trace-reconstructed sequence on the right, from Finding
   07. Built because a side-by-side visual makes the "what's visible
   vs. what's revealed" contrast land at a glance in a way Finding 07's
   own prose and code blocks don't — the same "does a chart add
   something a table doesn't" test the plan asked for elsewhere,
   applied here to a diagram instead of a plot.

## Figures skipped, and why

**W6 overflow timeline (plan item 5) — skipped.** The plan's own premise
was that W6's duration-based captures would show a `kOverflow` gap
marking the buffer wrap. Finding 12's Phase 9.3 correction already
established the opposite: across every W6 capture in the campaign,
**zero** `kOverflow` gaps ever appear — the phenomenon this chart was
built to visualize doesn't occur in this pipeline's own gap
classification (the physical buffer wrap is invisible to the decoder;
only the ordinary start-of-decode `noSync` appears). A timeline chart
with a marker that never fires would be either empty or misleading;
skipped rather than built for its own sake.

**W4 ISR cycle-cost breakdown (plan item 6) — skipped.** Finding 14
established that this vendored OpenCSD build cannot decode this
hardware's timestamp+cyclecount packet stream (`UNSYNC_BAD_PACKET`,
confirmed on every rich capture in the campaign) — the underlying
entry→return cycle data this chart needs was never obtained, on real
hardware or otherwise. Charting it would mean fabricating numbers.

Both omissions follow the same principle the plan itself states for
Phase 9.2 ("no chart... unless real divergence structure exists to
show — a table is more honest than a chart with nothing in it"),
applied here to two more cases where the underlying premise didn't
survive contact with real data.

## Caveats, stated honestly

- **Figure 3's percentages are computed from a single capture per
  (workload, configuration) cell** — N=1, per Finding 06/14's own
  standing caveat about that sweep; the figure does not imply a
  repeated measurement its data doesn't have.
- **No dark-mode variant, no interactive layer** — these are static
  print PDFs for a LaTeX thesis, not the dataviz skill's default HTML
  artifact target; the parts of that skill that apply here are form
  selection, one-axis-per-panel, fixed color-by-job, and label
  discipline, not its hover/tooltip/theme-toggle machinery.
